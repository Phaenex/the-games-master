Everything needed to open, preview, tune, and rebuild the night scene without losing work or chasing a bug someone already chased. Playing the build (walkthrough)

This is for actually playing the finished prologue, not for editing it. If you want to tune lighting instead, skip to Opening the project.

Don't just double-click the .app in Finder

Verified this session with spctl -a -vv: the build is ad-hoc signed, not notarized, and Gatekeeper rejects it outright when opened the normal way. Every automated test this session launched the binary directly from a terminal instead — which does not go through the same Gatekeeper check — so this would have been invisible until someone actually tried to double-click it.

The easy way

Double-click scripts/launch-wend-hill.command in Finder. It execs the binary directly, the same way every test this session did, so Gatekeeper never enters the picture. Built and smoke-tested this session — it launches the real game process cleanly.

If macOS itself questions the .command script the first time (a generic "unidentified developer" prompt some Mac configurations show for any new script, unrelated to the Gatekeeper rejection above): right-click it → Open → confirm, once. That override applies only to this tiny launcher, not to the game binary.

The manual way

"$HOME/GamesMaster-Unity/Builds/macOS-Wend/Wend Hill Prologue.app/Contents/MacOS/The Games Master"

Paste that into Terminal and press enter. Same effect as the launcher script.

What to expect

  • Windowed, 1600×900, resizable — not fullscreen, so it won't hijack the whole display.
  • Spawns at the start of the route already facing down it. WASD + mouse look, per GmPlayer.
  • Ambient audio starts immediately: a quiet wind bed, footsteps as you walk, occasional crickets/owl. First time this scene has had any sound at all — see the audio section of docs/WEND-NIGHT-LADDER.md for exactly what's reused vs. new.
  • The route runs to a lake at roughly 439m and stops there on purpose — see "Still open" below, that ending is a level design question, not a bug.

Pause shows no on-screen menu in this scene

Checked directly in GmPlayer.cs: pressing Escape freezes time and frees the mouse cursor (that cursor reappearing is the only visible sign anything happened) but renders no pause UI here — there's no pause-menu Canvas wired into Wend Hill. This is existing behaviour of the shared player controller, not something this pass changed, and building a real pause menu is out of scope for a "tighten before the walkthrough" pass. If the screen looks frozen and the mouse pointer is visible: that's pause, not a hang. Escape again resumes; Q while paused quits; and Cmd+Q (or just closing the window) always works as a fallback regardless of in-game state.

Verified this session, boot-to-idle: launched with zero flags, left running untouched for 30 real seconds, confirmed the process was still alive and the log had zero exceptions/errors. (Some benign Unity warnings about negative-scale colliders on purchased-pack geometry — SM_Wood_PlankWallWindow…, SM_Cliff… — are pre-existing pack quirks, not something introduced by recent work, and don't affect play.)

Opening the project

Unity Hub → open ~/GamesMaster-Unity. In the Project window:

Assets/Scenes/WendHill_Prologue.unity
Not this one

Don't open Assets/LeartesStudios/.../HDRP_Abandoned_Village.unity — that's the purchased source. WendHill_Prologue.unity is the already-built night version with everything committed: exposure, gap lamps, wall/grass de-tint, ambient audio, the works.

The scene file itself is not in git and shouldn't be — it's regenerated from the purchased source on every build. What is in git is the recipe that builds it: the C# under unity/scenes/wend-hill-prologue/.

The short version

Only menu item #1 is safe to click interactively. Every other one is written for the terminal — use the CLI reference below instead, which runs each of these in a separate headless process and leaves your open Editor session untouched.

Live preview workflow

Fastest way to see a lighting change — much faster than a screenshot-and-rebuild loop, since the Scene/Game view updates live as you drag a slider.

  1. With WendHill_Prologue.unity open, select the volume profile at Assets/Scenes/WendHill_NightProfile.asset. This is the actual recipe — Fog, HDRISky exposure, Exposure override, IndirectLightingController — everything GmWendNight.cs sets in code.
  2. Drag its sliders and watch the Scene view change in real time.
  3. To see it from the player's eye height: select the Player object, or hit Play. GmPlayer takes normal WASD + mouse, so you can walk it interactively instead of watching the automated walk probe do it.
  4. The moon / practicals: select the Directional Light (the moon) or any practical light directly in the Hierarchy and tweak intensity/color the normal Unity way.
No consequences

Exploring here is free — don't save the scene if you want to discard a tweak.

Making a change stick

None of it persists on its own

Every live tweak — the profile, the lights — gets overwritten the next time anyone rebuilds, because BuildCommittedNight always starts by re-copying the scene fresh from the purchased source and reapplying the recipe from code.

To keep a change, find the matching constant in GmWendNight.cs — e.g. DefaultSkyExposureDrop, DefaultExposureEV, the fog albedo/tint colors in SkyAndFogToNight() — and change it there.

That file lives at two paths that must stay in sync:

Repo (source of truth, what's committed)unity/scenes/wend-hill-prologue/Editor/GmWendNight.cs
Unity project (what the editor runs)~/GamesMaster-Unity/Assets/Editor/Scenes/wend-hill-prologue/GmWendNight.cs

Edit the repo copy, then push it into Unity:

npm run unity:scene:sync

Editing the Unity-side copy directly works in the editor but isn't tracked by git — copy it back to the repo path before it's forgotten, or just say the value out loud and have it changed + synced properly. This whole directory syncs automatically (any .cs file found under unity/scenes/wend-hill-prologue/), so a new file needs no registry edit, just the sync command.

Gotcha found this session #1 — the default scene is the WRONG one

node scripts/unity-cli.mjs rebuild with no scene id targets the registry's defaultScene, which is wend-hill — the retired estate scene (GmEstateBuilderV2.Build, Assets/Scenes/WendHill.unity) — not wend-hill-prologue. Running it bare silently rebuilds the wrong game. Always pass the id explicitly: rebuild wend-hill-prologue, audit wend-hill-prologue, etc. (Harmless if you do it by accident — it only touches the untracked legacy scene, nothing in git — but it wastes several minutes and can confuse a "why didn't my change show up" moment.)

Gotcha found this session #2 — don't run the walk with -nographics

Launching the built binary with -batchmode -nographics for a "quick" walk check produced 10 stalled waypoints in the first 3 metres — nothing like the real behaviour. Re-run identically except dropping -nographics (real window, still launched headlessly from a script, just not graphics-less) and the same short walk completed with 0 stalls. The build step itself is fine with -nographics; the walk/wall-test runs need a real window to move correctly. If a walk run looks like the NavMesh suddenly broke, check this flag before touching any pathing code.

Bisect flags

Command-line overrides so a single lever can move without editing code between runs — pass to the raw Unity binary invocation (build step) as extra args after -executeMethod GmWendNight.BuildCommittedNight. A run with no flags reproduces the committed night byte-for-byte, so a flagless run is always the control.

The EV sign is the single most expensive mistake in this project's history

It's been made twice. The applied multiplier is 2^(-fixedExposure), so a larger EV number is darker. Don't reason about it — bracket it, the way every value in the committed recipe below actually was.

Traps & hard-won lessons

The recurring failure shapes — read this before spending a session rediscovering one of these.

recurring bug

The same defect, three properties in a row

Foliage emission, wall base-tint, grass albedo intensity — all three are the identical shape: a shader property with a small bias that's a rounding error under the pack's 2000 lux daylight and becomes the dominant signal at this scene's night exposure. If a night-scene material reads wrong in colour rather than just brightness, check for a fourth instance of this before assuming it's a lighting problem.

lesson

Two agreeing measurements of the wrong vantage agree perfectly and tell you nothing

EV -1.0 was picked, confirmed by HDRP's own auto-exposure, and voided anyway — because both measurements were taken at a spawn point that was the mathematical centroid of 57 scattered road meshes, nowhere near the actual village street. Bracket from where the game actually happens, not from wherever is convenient to measure.

lesson

A build that compiles and passes a guard has demonstrated nothing about what it renders

The first prologue app built clean, passed its contract, and rendered the wrong camera (the pack ships 30 cameras; one was left enabled at the same depth as the player's). No editor frame could have shown it — every review rig renders a camera it creates and points by hand. The app has to be launched and looked at. Same shape caught the AudioListener bug one component later.

dead end, don't retry

The water-cut: 6 attempts, all recorded, none wired in

Truncating the route before it reaches the lake looks like a one-line raycast. It took 6 attempts across two sessions and the honest conclusion is: there is no static signal on this scene that separates a dry dip from a real drop, because the purchased pack ships no water collider and no lake mesh at the place that matters. RaycastGroundY, GroundNearWater, GroundInFootprint all stay in GmWendRoute.cs, tested and unused. The runtime stop in GmWendWalkProbe (checks the EYE against the water surface every frame) is the only thing that has ever correctly answered this. Don't re-attempt a static raycast fix without reading that section of the ladder doc first.

found this session

Gatekeeper rejects the built app on a normal double-click

Every automated test this session launched the binary directly from a terminal, which bypasses the LaunchServices Gatekeeper check that a Finder double-click goes through. spctl -a -vv on the built app confirms rejected — ad-hoc signed, not notarized. This would have been invisible right up until an actual human tried to open it the normal way. See "Playing the build" above for the launcher script that sidesteps it. Worth checking again after any future rebuild, in case a future Unity version or build setting changes the signing behaviour.

unexplained — still open

The review rig's forward-view reads 0.026 where the ladder reads 0.059, same position/EV

The rear view agrees between the two harnesses to ~1%. One hypothesis (temporal fog accumulation) was tested and disproven. Not settled — if you're chasing a forward-view number that looks too dark, check whether it's this known anomaly before trusting it.
